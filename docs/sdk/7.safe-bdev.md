# Safe BDev

**Safe BDev** (`clio_safe_bdev`) is a fault-tolerant virtual block device for the
Clio runtime. It stripes data across a set of member block devices and protects
it with **Reed–Solomon erasure coding**, so the array keeps serving data even
after one or more member drives fail. A CTE (Context Transfer Engine) can use a
safe-bdev as its backing store, and a clio-fs (POSIX filesystem) can sit on top
of the CTE — giving you a crash-consistent, self-healing filesystem.

At a glance:

- **Erasure coded**, not mirrored: `k` data drives + `m` parity drives tolerate
  up to `m` simultaneous drive failures at `m/(k+m)` overhead.
- **Grows without reshuffling**: add data or parity drives at runtime; existing
  data is never re-encoded or moved.
- **Self-healing**: a failed drive is reconstructed onto a replacement from the
  surviving drives, on demand (degraded reads) and in the background (rebuild).
- **Crash-consistent**: group geometry, allocator state, membership, and
  in-flight recovery all survive a restart — an interrupted rebuild *resumes*.

## Quick start: a clio-fs compose file with Safe BDev

A safe-bdev is assembled from ordinary `clio_bdev` member pools. A typical stack
is **member bdevs → safe-bdev → CTE → clio-fs**:

```yaml
runtime:
  num_threads: 4
  queue_depth: 1024

compose:
  # 1) Member block devices (the physical drives). Any bdev_type works
  #    (file, ram, ...). Here: three 256 MB file-backed data drives.
  - mod_name: clio_bdev
    pool_name: "/mnt/bdev0.dat"
    pool_query: local
    pool_id: "301.0"
    bdev_type: file
    capacity: "256MB"
    alloc_log: "/mnt/bdev0.alog"

  - mod_name: clio_bdev
    pool_name: "/mnt/bdev1.dat"
    pool_query: local
    pool_id: "302.0"
    bdev_type: file
    capacity: "256MB"
    alloc_log: "/mnt/bdev1.alog"

  - mod_name: clio_bdev
    pool_name: "/mnt/bdev2.dat"
    pool_query: local
    pool_id: "303.0"
    bdev_type: file
    capacity: "256MB"
    alloc_log: "/mnt/bdev2.alog"

  # 2) The safe-bdev over the data drives. `members` lists the INITIAL DATA
  #    members; parity is provisioned separately (see below). max_failures is
  #    the fault-tolerance TARGET (M).
  - mod_name: clio_safe_bdev
    pool_name: "safe0"
    pool_query: local
    pool_id: "350.0"
    max_failures: 1
    alloc_log: "/mnt/safe0.alog"   # crash-restart WAL (see "Crash restart")
    members:
      - pool_name: "/mnt/bdev0.dat"
        node_id: 0
        pool_id_major: 301
        pool_id_minor: 0
      - pool_name: "/mnt/bdev1.dat"
        node_id: 0
        pool_id_major: 302
        pool_id_minor: 0
      - pool_name: "/mnt/bdev2.dat"
        node_id: 0
        pool_id_major: 303
        pool_id_minor: 0

  # 3) A CTE bound to the safe-bdev as its backing store.
  - mod_name: clio_cte_core
    pool_name: cte_main
    pool_query: local
    pool_id: "512.0"
    storage:
      - path: "safe0"
        existing_pool_id: "350.0"
        existing_pool_module: "clio_safe_bdev"
        score: 1.0
    dpe:
      dpe_type: "max_bw"

  # 4) A clio-fs (POSIX filesystem) over the CTE.
  - mod_name: clio_cte_filesystem
    pool_name: clio_fs
    pool_query: local
    pool_id: "560.0"
    next_pool_id: "512.0"   # points at the CTE core
    targets:
      neighborhood: 1
```

**Key points about the compose file:**

- Each **member** is a normal `clio_bdev` pool. The safe-bdev references them by
  pool id (`pool_id_major` / `pool_id_minor`) — it does not create them.
- `members:` are the **initial data drives** only. **Parity is added at runtime**
  via `AddBdev(..., as_parity=1)` — `max_failures` just caps how much parity the
  array will accept. (A safe-bdev with `max_failures: 1` and three data members
  tolerates one failure once one parity drive has been added, giving a 3+1
  layout.)
- The CTE binds to the safe-bdev with `existing_pool_id` /
  `existing_pool_module` instead of declaring its own storage.
- The clio-fs is mounted via the FUSE adapter (`clio_cte_fuse <mountpoint>`) and
  routes through the CTE, which stores blob bytes on the safe-bdev.

A ready-to-run, fully containerized example (runtime + safe-bdev + CTE + clio-fs
+ dashboard) lives at
`context-runtime/test/integration/safe-bdev/` in the source tree.

## How Safe BDev works

### Members, roles, and geometry

A safe-bdev is a set of **member** block devices in two roles:

- **Data members** (`k` of them) hold striped user data.
- **Parity members** (`m` of them) hold Reed–Solomon parity.

Fixed geometry:

| Quantity | Value | Notes |
|---|---|---|
| **Chunk (stripe unit)** | 64 KiB | The RAID-0 shard / parity chunk size. |
| **Superblock** | 64 KiB | Reserved at absolute offset 0 of every member. |
| **Member usable region** | begins at offset 64 KiB | Row `r`'s chunk on a member is at `64 KiB + r · 64 KiB`. |

Every member (data or parity) stores exactly one 64 KiB **chunk** per **global
row**. Data member `d` stores the data shard for its column; parity member `j`
stores the `j`-th RS parity shard for that row.

### Append-only stripe groups

Instead of a single fixed width, a safe-bdev is a sequence of **append-only
groups**. Each group freezes its data-drive width `k_g` when it opens and owns a
contiguous band of global rows:

```
Group 0: rows [0,   R0)   width k0   code RS(k0, m)
Group 1: rows [R0,  R1)   width k1   code RS(k1, m)   (k1 > k0)
Group 2: rows [R1,  R2)   width k2   code RS(k2, m)   (k2 > k1)
...
```

Within a group, user data is **RAID-0 striped** across its `k_g` data members;
across groups, all groups share the same `m` **parity members**. Each group
therefore runs its own Reed–Solomon code `RS(k_g, m)`. A logical byte offset
maps to `(group, row, data_column, byte-within-chunk)`; the current (widest,
last-opened) group is where new allocations come from.

This structure is what makes growth cheap — see
[Incremental growth](#incremental-growth--dynamic-erasure-coding).

### Reads, degraded reads, and reconstruction

- **Healthy read**: data is read directly from the data members.
- **Degraded read**: if a data member is down (auto-faulted on a fatal device
  error, or explicitly removed), its chunk is **reconstructed on demand** by
  reading `k_g` survivors from that row (remaining data members + parity) and RS
  decoding. Reads keep succeeding as long as no more than `m` members are down.

A row can only be reconstructed when its **parity is current** (see below).

### Asynchronous parity

Writes are kept off the parity critical path:

1. A **write** stores the data chunks immediately and marks each touched global
   row **dirty** (parity not yet current).
2. A background **`BuildParity`** task (every ~50 ms) drains the dirty set,
   recomputes each row's parity shards under its group's code, and writes them
   to the parity members — clearing the row once parity is durable.

Because reconstruction requires current parity, a row that is still dirty is not
reconstructable; flush parity (or let `BuildParity` converge) before relying on
degraded reads for freshly written data. The `dirty_rows` counter is exposed in
the monitor stats.

## Incremental growth & dynamic erasure coding

Drives are added **one at a time, at runtime**, and existing data is **never
re-encoded or moved**. This is the "dynamic erasure coding" property.

### Adding a data drive (`AddBdev`, `as_parity=0`)

Adding a data drive:

1. **Freezes** the current (widest) group at its **high-water mark** — the
   number of rows it has actually used so far.
2. **Opens a new group** of width `k + 1` over the remaining physical rows.

Existing groups keep their frozen width and code `RS(k_g, m)`; only *new*
allocations land in the wider group `RS(k_g+1, m)`. No data is reshuffled.

The tradeoff is **storage efficiency vs. write width**: wider groups amortize
the same `m` parity drives over more data (`m/(k+m)` shrinks as `k` grows), so
adding data drives makes future writes more space-efficient without touching
what's already stored.

### Adding a parity drive (`AddBdev`, `as_parity=1`)

Adding a parity drive raises fault tolerance toward `max_failures`:

1. Appends a parity member and increments the parity level `m`.
2. Re-marks all written rows **dirty** so `BuildParity` recomputes the
   now-higher parity level in the background.

`max_failures` (M) is the **cap**: the array refuses parity beyond M. Provision
parity from 0 up to M as your durability needs grow.

### Removing and replacing a drive

- **`RemoveBdev`** marks a member *faulty* (a recovery candidate) or *removed*
  (a clean unlink). The slot is never erased — state is positional. Degraded
  reads take over immediately.
- **`RecoverBdev`** reconstructs a failed member's shards onto a **fresh
  replacement** drive. It reads survivors, RS-decodes (data) or re-encodes
  (parity) every row the member participates in, and writes them to the new
  drive. The replacement stays excluded from reads (degraded path) until the
  rebuild completes, then comes online.

The typical operator flow — **remove the failed drive, add a replacement to
trigger recovery** — is exposed as a one-click "Replace + recover" action in the
context-visualizer safe-bdev dashboard, alongside live **recovery progress**
(operations in flight vs. remaining). The same counters are available in the
monitor stats: `recovery_active`, `recovery_ops_total`,
`recovery_ops_completed`, `recovery_ops_in_flight`, `recovery_ops_remaining`.

## Crash restart & durability

A safe-bdev reconstructs its entire logical state from on-disk metadata after a
restart. Three persistence mechanisms cooperate; enabling them requires only
that the `alloc_log` path is set in the config.

### 1. Member superblocks

Each member reserves a **64 KiB superblock** at offset 0 recording the array
identity (`major.minor`), the member's role and index, `max_failures`, and a
checksum. On restart every configured member is probed:

- **present and ours** → **re-attach** (reuse in place; member pool ids may even
  differ across restarts — members are recognized by superblock, not id);
- **blank** → **initialize** a fresh member;
- **present but foreign** → **refuse** (another array owns the drive).

### 2. Allocator-state WAL (`alloc_log`)

The append-only **group geometry** (`LogGroupOpen` / `LogGroupFreeze`) and every
**block allocation/free** (`LogAlloc` / `LogFree`) are journaled to the
`alloc_log` file. On restart the log is replayed to reconstruct the groups and
each group's allocator **without re-handing-out any still-live logical offset**.
The log is flushed and **compacted** periodically (every ~50 ms): compaction
rewrites it down to one group-open per group plus one record per live block once
the on-disk record count exceeds `max(1024, live · 4)`, bounding its size.

### 3. Durable membership + recovery resume (member manifest)

The config's `members:` list names only the *startup* data drives — it cannot
express runtime-added parity drives or the state of an in-flight recovery. A
small **member manifest** (`<alloc_log>.members`) closes that gap. It records the
**current full membership** (data + parity, each member's role/index/pool/state)
and the **recovery flag** for any drive mid-rebuild, and is rewritten atomically
(temp file + rename) on every membership change (create / add / remove /
recover).

On restart, `Create`:

1. re-attaches **data** members from the config by superblock identity;
2. restores **runtime-added parity** members from the manifest (probing each by
   superblock; stale entries are skipped);
3. marks any member left **mid-recovery** as recovering (excluded from reads),
   and then **resumes and completes the rebuild**.

Because the rebuild is **idempotent** (it reconstructs and rewrites every one of
the member's rows), re-running a recovery that was interrupted by a crash is
safe: partial progress is simply overwritten, and the replacement drive is never
trusted for reads until it is fully rebuilt. The net guarantee: **an interrupted
recovery survives a restart and finishes, and data is fully recovered** with no
window of silent corruption.

## Metadata overheads

| Source | Overhead | Scaling |
|---|---|---|
| **Superblock** | **64 KiB per member**, reserved at offset 0 | Fixed per member, independent of capacity. |
| **Parity storage** | `m` parity drives | The erasure-coding cost: `m/(k+m)` of raw capacity for an `RS(k, m)` group. Wider (higher-`k`) groups lower this. |
| **Chunk granularity** | 64 KiB stripe unit | A write smaller than a stripe still consumes whole 64 KiB chunks per touched row. |
| **Allocator WAL** (`alloc_log`) | One file; ~one group-open per group + one record per **live block** after compaction | Grows with live-block count; capped by compaction at `max(1024, live · 4)` records on disk. |
| **Member manifest** (`<alloc_log>.members`) | A few dozen bytes per member (role, index, pool id, node, state, name) | Bounded by member count (a handful of drives); rewritten in full on each membership change. |
| **In-memory group metadata** | Per-group RS codec + allocator (block map + heap) | One set per group; the number of groups is capped (default 64). |

Practical notes:

- The **superblock is the only fixed capacity tax** on each drive; everything
  else scales with usage (parity/data ratio, live blocks) or with the small,
  bounded number of drives (manifest).
- Both the WAL and the manifest live next to the safe-bdev's `alloc_log` path;
  keep that on durable, low-latency storage.

## Monitoring

Query the pool's monitor for live state (also surfaced by the context-visualizer
safe-bdev dashboard):

```
Monitor("stats") ->
  pool_name, max_failures, data_count, parity_level, num_groups, total_rows,
  dirty_rows, reattached_members, alloc_log_records,
  recovery_active, recovery_ops_total, recovery_ops_completed,
  recovery_ops_in_flight, recovery_ops_remaining,
  members: [ { role, index, pool_name, pool_id, state, recovering } ]
```

- `dirty_rows` — rows whose parity is not yet current.
- `parity_level` vs `max_failures` — how much of the target fault tolerance is
  currently provisioned.
- `recovery_*` — live rebuild progress (in flight vs remaining); `members[].state`
  reports `active` / `faulty` / `removed` / `recovering`.
