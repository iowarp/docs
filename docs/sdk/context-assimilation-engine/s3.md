# Amazon S3 Connector

## Overview

The S3 connector lets the Context Assimilation Engine (CAE) import objects from [Amazon S3](https://aws.amazon.com/s3/), or any S3-compatible object store such as [MinIO](https://min.io/), into IOWarp. Each object named in an OMNI file is streamed straight from S3 into a CTE tag.

The connector is implemented by `S3FileAssimilator` and is conditionally compiled with the `CAE_ENABLE_S3` CMake flag.

Objects are read **in-process** inside the runtime: the assimilator signs each request itself (AWS Signature Version 4) and streams it over HTTPS with [POCO](https://pocoproject.org/). The AWS SDK for C++ is never loaded into the runtime, because its load-time initialization corrupts CLIO Runtime startup. The SDK is used only by the standalone [`cae_s3_tool`](#the-cae_s3_tool-helper) helper.

:::note Not the S3 storage tier
This page covers **importing** S3 objects through CAE. Using an S3 bucket as a CTE **storage tier** (the `s3` block device) is a separate feature with its own build flag and its own credential rules. See [Configuration → Storage Tiers](../../deployment/configuration#storage-tiers-storage).
:::

## Prerequisites

### Build Dependencies

| Dependency | Purpose |
|-----------|---------|
| [POCO](https://pocoproject.org/) (Net, NetSSL, Crypto, Foundation) | In-process HTTPS reads and SigV4 signing inside the runtime |
| [AWS SDK for C++](https://github.com/aws/aws-sdk-cpp) (`s3` component) | Builds the out-of-process `cae_s3_tool` helper only |

Both are required. If either is missing, CMake warns and S3 import is disabled.

### Build with S3 Support

```bash
cmake --preset release -DCAE_ENABLE_S3=ON
cmake --build build
```

Verify that the configure output includes:

```
found AWS SDK + Poco (CAE S3 support: ENABLED)
```

If you instead see `S3 import will be disabled.`, the warning just above it names the missing dependency: the AWS SDK (`aws-sdk-cpp`) or POCO (`libpoco-dev` on Debian/Ubuntu).

With Spack, enable the `s3_cae` variant (CAE itself is on by default):

```bash
spack install iowarp +s3_cae
```

:::note Variant rename
This variant used to be called `+s3`. It was renamed to `+s3_cae` so it is not confused with `+s3_bdev`, which builds the S3 **storage tier** and has different dependencies.
:::

### AWS Account

You need a bucket and an access key whose IAM policy allows `s3:GetObject` on the objects you import. Also grant `s3:ListBucket` on the bucket: without it, S3 reports a missing key as HTTP 403 instead of 404, which hides the real cause.

## Credentials and Region

Credentials and region are resolved **inside the runtime process** (the `clio_run` daemon hosting the CAE pool), once per imported object. The environment of the `clio_cae` client that submits the OMNI file is **not** consulted, so export the variables in the shell (or job script) that starts the runtime.

Only the profile **name** ever travels in a task, so secret keys never appear in an OMNI file or task payload. They stay in the runtime's environment or credentials file.

### Credential resolution

Highest priority first:

1. **Environment keys.** `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` (plus `AWS_SESSION_TOKEN` for temporary credentials). Both the key ID and the secret must be set for this step to apply.
2. **Credentials file.** Otherwise, read a profile section from the shared credentials file:
   - **Profile:** `AWS_PROFILE`, else `default`.
   - **File:** `AWS_SHARED_CREDENTIALS_FILE`, else `~/.aws/credentials` (the runtime process's `$HOME`).
   - **Keys read:** `aws_access_key_id`, `aws_secret_access_key`, and the optional `aws_session_token`.

Only static keys are supported. SSO profiles, `credential_process`, EC2/ECS instance roles and `role_arn` assume-role chains are **not** resolved. Export temporary keys into the environment instead.

### Region resolution

Highest priority first:

1. `AWS_DEFAULT_REGION`
2. `AWS_REGION`
3. The `region` key in the config file: `AWS_CONFIG_FILE`, else `~/.aws/config`. Section `[default]` for the default profile, `[profile <name>]` (or `[<name>]`) for a named one.

There is **no fallback region**. If none of these is set, the import fails rather than guessing `us-east-1`, because a wrong region makes S3 answer HTTP 301, which the signer does not follow.

### Example

```ini
# ~/.aws/credentials   (chmod 600)
[clio-bench]
aws_access_key_id = AKIA...
aws_secret_access_key = ...
```

```ini
# ~/.aws/config
[profile clio-bench]
region = us-east-2
```

```bash
# In the shell that starts the runtime
export AWS_PROFILE=clio-bench
clio_run start
```

## S3-Compatible Endpoints (MinIO)

Set `S3_ENDPOINT` in the runtime's environment to target an S3-compatible server:

```bash
export S3_ENDPOINT=http://127.0.0.1:9000
export AWS_DEFAULT_REGION=us-east-1     # still required; MinIO accepts us-east-1
export AWS_ACCESS_KEY_ID=minioadmin
export AWS_SECRET_ACCESS_KEY=minioadmin
clio_run start
```

| `S3_ENDPOINT` | Addressing | Request URL |
|---------------|-----------|-------------|
| unset | Virtual-hosted (real AWS) | `https://<bucket>.s3.<region>.amazonaws.com/<key>` |
| set | Path-style | `<S3_ENDPOINT>/<bucket>/<key>` |

A trailing `/` on the endpoint is stripped.

:::caution `AWS_ENDPOINT_URL` is not read by the runtime
The in-process assimilator reads only `S3_ENDPOINT`. `AWS_ENDPOINT_URL` is honored by `cae_s3_tool` (through the AWS SDK) but **not** by the runtime, so a setup that relies on it will seed objects into MinIO with the helper and then try to read them from real AWS.
:::

## OMNI File Format for S3

### `s3://` URI

```yaml
name: s3_import

transfers:
  - src: s3://my-bucket/path/to/object.bin
    dst: iowarp::my_dataset
    format: binary
    depends_on: ""
    range_off: 0
    range_size: 0
```

| Field | Notes |
|-------|-------|
| `src` | `s3://<bucket>/<key>`. The `s3::<bucket>/<key>` form is also accepted. The key must be non-empty: a bare `s3://<bucket>` is rejected. |
| `dst` | Must be `iowarp::<tag_name>`. No other destination protocol is supported. |
| `format` | `binary`. The object is stored as opaque bytes. |
| `range_off` / `range_size` | `range_size: 0` imports the whole object. A positive `range_size` imports bytes `[range_off, range_off + range_size)` with a ranged GET. A bare `range_off` with `range_size: 0` still means the whole object. |

Submit it with `clio_cae`, the same as any OMNI file:

```bash
clio_cae /path/to/s3_import.yaml
```

### What lands in CTE

For each transfer, the assimilator gets or creates the destination tag and writes:

| Blob | Contents |
|------|----------|
| `description` | `binary<size=<bytes>, offset=<range_off>>` |
| `chunk_0`, `chunk_1`, … | The object body, in chunks of up to 1 MB |

Body chunks are written with up to 32 `PutBlob` operations in flight. If the HTTPS connection drops mid-object, the assimilator resumes with a ranged GET from the last byte received (up to 16 times per object) instead of failing the import.

Keep-alive connections are pooled per runtime and reused across objects, so a batch of many small objects does not pay a TLS handshake each. The assimilator never creates a bucket.

## Quick Start

### 1. Build with S3 Support

```bash
cmake --preset release -DCAE_ENABLE_S3=ON
cmake --build build && cmake --install build
```

### 2. Provide Credentials to the Runtime

Either export keys:

```bash
export AWS_ACCESS_KEY_ID=...
export AWS_SECRET_ACCESS_KEY=...
export AWS_DEFAULT_REGION=us-east-2
```

or point at a profile in `~/.aws/credentials`:

```bash
export AWS_PROFILE=my-profile
```

### 3. Start the Runtime with CTE and CAE

Start `clio_run` **from the same shell**, with a config whose `compose` section includes `clio_cte_core` and `clio_cae_core` (the shipped default does):

```bash
clio_run start
```

### 4. Import

```bash
clio_cae s3_import.yaml
```

## The `cae_s3_tool` Helper

When `CAE_ENABLE_S3` is on, the build also installs `cae_s3_tool` to `bin/`. It is a small standalone program that links the AWS SDK, so it never runs inside the runtime. It is handy for seeding a bucket, fetching an object to compare against what landed in CTE, or checking credentials outside the runtime.

```text
cae_s3_tool get <bucket> <key> <out_path> [range_off range_size]
cae_s3_tool put <bucket> <key> <in_path>
cae_s3_tool del <bucket> <key>
```

- **`put`** also creates the bucket if it is missing (best effort).
- **`del`** treats a missing object as success.
- **Exit status:** `0` on success; non-zero with a message on stderr otherwise.

The helper resolves its configuration through the **AWS SDK**, so it accepts more than the runtime does:

| Setting | Read from |
|---------|-----------|
| Credentials | The SDK's default provider chain (environment, profiles, SSO, instance roles, …) |
| Region | `AWS_DEFAULT_REGION`, default `us-east-1` |
| Endpoint | `S3_ENDPOINT` or `AWS_ENDPOINT_URL` (path-style) |
| Anonymous access | `AWS_NO_SIGN_REQUEST=1` forces unsigned requests (public buckets such as the AWS Open Data registry). If the chain finds no credentials, it also falls back to anonymous. |

:::caution
Because the helper's credential chain is broader, `cae_s3_tool get` can succeed where an import fails. A working helper proves the bucket and key are readable. It does not prove the runtime can resolve the same credentials (see [Credentials and Region](#credentials-and-region)).
:::

## Error Codes

The `S3FileAssimilator::Schedule` method returns the following error codes:

| Code | Description |
|------|-------------|
| 0 | Success |
| -1 | Invalid destination protocol (not `iowarp`) |
| -2 | Destination URI has no tag name |
| -3 | Failed to get or create the destination tag in CTE |
| -4 | Invalid S3 source URI (missing bucket or key) |
| -6 | Credentials or region could not be resolved (the log names the profile and file tried) |
| -7 | Object not found, or the GET request failed |
| -8 | Short or failed read on a body chunk (after resume attempts) |
| -9 | Failed to store the `description` blob |
| -10 | A body `PutBlob` failed |

If the build lacks S3 support, the factory logs `S3 protocol requested but S3 support not compiled in. Rebuild with -DCAE_ENABLE_S3=ON to enable S3 support.` and no assimilator is created.

## Troubleshooting

### `CAE S3 support` is missing from the configure output

The configure step printed `S3 import will be disabled.` Install whichever dependency the preceding warning names (`aws-sdk-cpp`, or POCO's Net/NetSSL/Crypto components) and reconfigure.

### `AWS credentials: no profile [<name>] in the credentials file`

The runtime found no `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` pair, fell back to the credentials file, and that file has no `[<name>]` section. Check:
- `AWS_PROFILE` is spelled correctly in the **runtime's** environment.
- The file exists under the runtime user's `$HOME`, or set `AWS_SHARED_CREDENTIALS_FILE`.
- Credentials files use `[name]`, not `[profile name]`; that form belongs in `~/.aws/config`.

### `profile [<name>] is missing aws_access_key_id / aws_secret_access_key`

The section exists, but one of the two keys is absent, or it is indented, which makes the parser treat it as a nested setting. Keys must start at column 0.

### `AWS region unresolved for profile [<name>]`

Set `AWS_DEFAULT_REGION` (or `AWS_REGION`) in the runtime's environment, or add `region = ...` to the profile in `~/.aws/config`.

### HTTP 301

The region does not match the bucket's region. Find the bucket's real region (the S3 console shows it) and set `AWS_DEFAULT_REGION` to it.

### HTTP 403

The keys are wrong or expired (temporary credentials need `AWS_SESSION_TOKEN`), the IAM policy lacks `s3:GetObject`, or the host clock is more than 15 minutes off, which invalidates SigV4 signatures. A missing key also returns 403 when the policy lacks `s3:ListBucket`.

### `object not found: s3://<bucket>/<key>`

The key does not exist. Keys are case-sensitive and have no leading `/`. With `S3_ENDPOINT` set, confirm you are pointed at the store you seeded.

### Imports work in your shell but fail under a launcher

The runtime daemon did not inherit your environment. Launchers that start `clio_run` on other nodes (pssh, Slurm prologs, Jarvis) pass a curated environment, so `AWS_*` variables exported in your shell or job script may never reach it. Export them where the daemon is started. With the `jarvis_clio_core` runtime package, list them in its `forward_env` parameter.
