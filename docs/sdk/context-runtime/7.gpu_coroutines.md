# GPU Coroutines

This guide covers the GPU coroutine system: C++20 `co_await` / `co_return` in CUDA `__device__` functions. GPU coroutines enable a task running on the GPU work orchestrator to **yield** mid-execution and be resumed later, using the same `chi::TaskResume` / `chi::yield()` API as CPU-side coroutines.

**Source:** `context-runtime/compiler/include/chimaera/gpu_coroutine.h`

## Overview

The Chimaera runtime supports cooperative multitasking on both CPU workers and the GPU work orchestrator. The GPU coroutine system uses the **same API names** as the CPU side (`chi::TaskResume`, `chi::RunContext`, `chi::yield()`), so module code is source-portable between CPU and GPU targets.

| | CPU | GPU |
|---|---|---|
| Compiler | GCC / Clang (host) | **Clang only** (via `add_cuda_executable`) |
| Context | Thread-local storage | Explicit `RunContext&` parameter |
| Frame allocation | `CHI_IPC->AllocateBuffer` | Device `malloc` (BuddyAllocator planned) |
| Scheduler | Worker blocked-task queue | `CoroutineScheduler` (fixed-capacity array) |
| Yield | `co_await chi::yield()` | `co_await chi::yield()` |
| Return type | `chi::TaskResume` | `chi::TaskResume` |

### Why Clang?

NVCC does not support C++20 coroutines in device code. Clang 18+ does, using its native `__builtin_coro_*` intrinsics. The standard library's `<coroutine>` header lacks `__device__` annotations, so the GPU coroutine system provides a custom replacement (`gpu_coroutine_handle.h`) that wraps the Clang builtins directly.

Files using GPU coroutines are compiled with Clang via the `add_cuda_executable()` or `add_cuda_library()` CMake functions (which automatically use Clang when `wrp_core_find_clang_cuda()` has been called). The rest of the runtime remains NVCC-compiled; the two link together normally.

## Architecture

```
GPU Work Orchestrator (persistent kernel)
  │
  │  PollOnce loop
  │  ├── Dequeue task from gpu2gpu queue
  │  ├── Dispatch: auto coro = container->RunCoro(ctx, task)
  │  ├── coro.resume()
  │  │     └── Coroutine runs until co_return or co_await chi::yield()
  │  ├── if coro.done() → complete task
  │  ├── else → scheduler.Insert(coro.release(), ctx)
  │  │
  │  └── scheduler.ResumeSuspended()
  │        ├── Decrement spin counters
  │        ├── Resume ready coroutines
  │        └── Remove completed entries
```

The `CoroutineScheduler` holds up to 32 suspended coroutines in a fixed-size array. Each iteration of the poll loop, it scans the array, decrements spin counters, and resumes any coroutine whose counter has reached zero.

## Core Types

### RunContext

Per-coroutine execution context passed explicitly to every coroutine function (no TLS on GPU). Same name as the CPU-side `chi::RunContext`.

```cpp
struct RunContext {
  std::coroutine_handle<> coro_handle_;  // Coroutine handle
  bool is_yielded_;                       // Set by yield awaiter on suspend
  u32 yield_spin_count_;                  // Requested spin count
  u32 spins_remaining_;                   // Countdown managed by scheduler
  u32 block_id_;                          // CUDA block index
  u32 thread_id_;                         // CUDA thread index within block
  void *heap_alloc_;                      // BuddyAllocator (future)
};
```

### TaskResume

The coroutine return type. Same name as `chi::TaskResume` on the CPU.

```cpp
__device__ TaskResume my_task(RunContext &ctx, int *data) {
  // Phase 1
  *data = compute_phase1();
  co_await chi::yield();  // Yield back to worker

  // Phase 2 (resumed later)
  *data += compute_phase2();
  co_return;
}
```

`TaskResume` is move-only. When it goes out of scope, it destroys the coroutine frame. Use `release()` to transfer ownership to the scheduler.

### YieldAwaiter / `chi::yield()`

Factory function that creates an awaitable for yielding:

```cpp
co_await chi::yield();        // Resume on the next poll iteration
co_await chi::yield(10);      // Skip 10 poll iterations before resuming
```

The spin count parameter is useful for I/O-bound tasks that know the result won't be ready for several iterations.

### CoroutineScheduler

Fixed-capacity scheduler for suspended coroutines. One per GPU block.

```cpp
CoroutineScheduler sched;

// After a coroutine yields:
auto handle = coro.release();
sched.Insert(handle, ctx);

// Each poll iteration:
sched.ResumeSuspended();
```

| Method | Description |
|--------|-------------|
| `Insert(handle, ctx)` | Add a yielded coroutine. Returns `false` if full. |
| `ResumeSuspended()` | Scan entries, decrement spin counters, resume ready coroutines, remove completed ones. |
| `Count()` | Number of currently suspended coroutines. |
| `HasSuspended()` | Whether any coroutines are suspended. |

## Nested Coroutines

GPU coroutines support nesting via symmetric transfer. When one coroutine `co_await`s another `TaskResume`, control transfers to the inner coroutine. When the inner completes, control returns to the outer automatically.

```cpp
__device__ TaskResume inner_work(RunContext &ctx, int *val) {
  *val += 100;
  co_return;
}

__device__ TaskResume outer_work(RunContext &ctx, int *val) {
  *val += 1;
  co_await inner_work(ctx, val);   // Symmetric transfer to inner
  *val += 1;                        // Resumes here after inner completes
  co_return;
  // val == 102
}
```

The `RunContext` is automatically propagated from outer to inner. The inner coroutine's `final_suspend` uses symmetric transfer (`await_suspend` returns the caller's handle) to resume the outer without extra stack frames.

## CMake Integration

### Build Functions

The standard `add_cuda_executable()` and `add_cuda_library()` functions automatically use Clang when `wrp_core_find_clang_cuda()` has been called. No special flags are needed -- the same call works with both NVCC and Clang.

```cmake
# Executable
add_cuda_executable(my_target FALSE my_file.cu
    INCLUDE_DIRS ${PROJECT_SOURCE_DIR}/compiler/include
    LINK_LIBS my_library
)

# Library (SHARED or STATIC)
add_cuda_library(my_lib SHARED FALSE impl.cu
    INCLUDE_DIRS ${PROJECT_SOURCE_DIR}/compiler/include
    LINK_LIBS some_dependency
)
```

| Parameter | Description |
|-----------|-------------|
| `INCLUDE_DIRS` | Additional include directories (optional) |
| `LINK_LIBS` | Libraries to link (optional) |

When Clang is the active compiler, the functions automatically:
- Derive `--cuda-path` from `CMAKE_CUDA_COMPILER`
- Use `CMAKE_CUDA_ARCHITECTURES` for `--cuda-gpu-arch=sm_XX`
- Link `cudart`
- Compile with `-std=c++20`

### Enabling in Your Project

In your component's `CMakeLists.txt`, call `wrp_core_find_clang_cuda()` after enabling CUDA:

```cmake
if(WRP_CORE_ENABLE_CUDA)
    wrp_core_enable_cuda(17)
    wrp_core_find_clang_cuda()
endif()
```

Then add your target as usual:

```cmake
if(WRP_CORE_ENABLE_CUDA OR WRP_CORE_ENABLE_ROCM)
    add_cuda_executable(my_gpu_coroutine_test FALSE test_gpu_coroutine.cu
        INCLUDE_DIRS ${CHIMAERA_ROOT}/compiler/include
    )
endif()
```

## Writing a GPU Coroutine

### Step 1: Include the Header

```cpp
#include <chimaera/gpu_coroutine.h>

using chi::RunContext;
using chi::CoroutineScheduler;
using chi::TaskResume;
```

This header must be included **before** any standard library header that might transitively pull in `<coroutine>`. It blocks the standard header and provides GPU-compatible replacements.

### Step 2: Write a Coroutine Function

Every GPU coroutine function must:
1. Return `TaskResume`
2. Take `RunContext &ctx` as its **first** parameter
3. Be marked `__device__`
4. Use `co_await` or `co_return` (at least one to make it a coroutine)

```cpp
__device__ TaskResume process_data(RunContext &ctx,
                                    float *input, float *output,
                                    int n) {
  // Phase 1: transform
  for (int i = 0; i < n; ++i) {
    output[i] = input[i] * 2.0f;
  }

  co_await chi::yield();  // Let other tasks run

  // Phase 2: reduce
  float sum = 0.0f;
  for (int i = 0; i < n; ++i) {
    sum += output[i];
  }
  output[0] = sum;
  co_return;
}
```

### Step 3: Drive from a Kernel

```cpp
__global__ void worker_kernel(float *input, float *output, int n) {
  RunContext ctx;
  CoroutineScheduler sched;

  // Create and start the coroutine
  auto coro = process_data(ctx, input, output, n);
  coro.resume();  // Runs until first yield or co_return

  if (!coro.done()) {
    // Coroutine yielded -- insert into scheduler
    sched.Insert(coro.release(), ctx);
  }

  // Poll loop
  while (sched.HasSuspended()) {
    sched.ResumeSuspended();
  }
}
```

### Step 4: Set CUDA Stack Size

The `CoroutineScheduler` uses ~1.3 KB of stack space (32 entries). CUDA's default kernel stack is 1 KB, which is insufficient. Increase it before launching:

```cpp
cudaDeviceSetLimit(cudaLimitStackSize, 8192);  // 8 KB
```

## Memory Model

Coroutine frames are allocated on the device via `promise_type::operator new`, which currently calls device `malloc`. A future integration will use `CHI_IPC->AllocateBuffer` backed by the per-thread `BuddyAllocator` (`CHI_GPU_HEAP`), which supports individual `free()` calls. The `ArenaAllocator` is **not** suitable because arenas are bulk-reset after each task batch, which would invalidate suspended coroutine frames.

The `RunContext::heap_alloc_` field is reserved for this purpose. When the allocator integration is complete, `promise_type::operator new` will allocate from the BuddyAllocator via this pointer.

## Custom Coroutine Handle

**Source:** `context-runtime/compiler/include/chimaera/gpu_coroutine_handle.h`

Neither libstdc++ nor libc++ annotate `std::coroutine_handle` methods with `__device__`. The GPU coroutine system replaces the standard header entirely by:

1. Defining `_GLIBCXX_COROUTINE` and `_LIBCPP_COROUTINE` to block the standard headers
2. Providing `std::coroutine_handle<T>` in the `std` namespace with `__host__ __device__` annotations
3. Using Clang's `__builtin_coro_resume`, `__builtin_coro_destroy`, `__builtin_coro_done`, `__builtin_coro_promise`, and `__builtin_coro_noop` directly

This header must be included before any transitive include of `<coroutine>`.

## Limitations

- **Clang-only**: `.cu` files using GPU coroutines cannot be compiled with NVCC. Use `add_cuda_executable()` / `add_cuda_library()` with `wrp_core_find_clang_cuda()` enabled.
- **Single-thread per block**: The coroutine scheduler is designed for thread-0 dispatch. Multi-threaded coroutine execution within a block is not supported.
- **Fixed scheduler capacity**: `CoroutineScheduler` holds at most 32 suspended coroutines. Exceeding this causes `Insert()` to return `false`.
- **No exception handling**: `unhandled_exception()` calls `__trap()` (device abort). GPU coroutines should not throw.
- **Stack size**: Kernels using `CoroutineScheduler` need `cudaDeviceSetLimit(cudaLimitStackSize, 8192)` or higher.
